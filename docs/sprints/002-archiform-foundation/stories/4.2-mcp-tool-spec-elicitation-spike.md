# Story 4.2: Generate MCP Tool Spec + Spike MCP Elicitation Against Pinned SDK

**User Story**: As an agent caller, I want an MCP tool spec generated from the action manifest such that each Memory Palace action becomes one MCP tool (name from action key, description from `summary`, input schema from `inputs`, confirmation routed through MCP elicitation), with a spike confirming MCP elicitation is supported in the pinned MCP SDK version, so that LLM agents can drive Memory Palace without bespoke per-projection code.
**FRs**: FR9
**Decisions**: D-019 (action manifest), D-035 (closed sets typed in tool spec), TC7 (pinned dependency floor — MCP SDK pinned)
**Complexity**: medium
**Test Tier**: smoke

## Acceptance Criteria
- **AC1** [happy — MCP tool spec generated]: Given Story 3.1's manifest and the codegen flow, When `bun run codegen` runs, Then `src/lib/generated/palace-mcp-tools.ts` is emitted with NFR9 provenance header; the file exports one MCP tool spec per manifest action with: tool name = action key (e.g., `palace.mint`), description = manifest's `summary`, inputSchema = manifest's `inputs` translated to JSON Schema (the source dialect), and an action-router callback wired to the generated TS client from Story 4.1.
- **AC2** [happy — input schema validates with same Valibot]: Given a generated MCP tool spec, When an LLM invokes `palace.mint` with input `{ name: "foo", mythosTemplate: "basic" }`, Then the tool's input is validated by the SAME Valibot validator the CLI uses (regenerated from the manifest in Story 3.1); validation errors surface to the MCP client per FR9 acceptance.
- **AC3** [spike — MCP elicitation supported in pinned SDK]: Given the pinned MCP SDK version in `package.json`, When the spike at `tests/mcp/elicitation-spike.test.ts` runs an end-to-end elicitation flow against the SDK, Then the test confirms support; the Dev Agent Record records the SDK version + elicitation API shape used.
- **AC4** [happy — `requiresConfirmation` routes to elicitation]: Given the `rename-mythos` manifest entry with `attributes.requiresConfirmation: true`, When an LLM invokes `palace.rename-mythos`, Then the tool surfaces an MCP elicitation step (using the manifest's `confirmationMessage`) rather than executing on first call; second-call after elicitation-grant proceeds.
- **AC5** [error — elicitation NOT supported fallback]: Given AC3 fails (MCP elicitation NOT supported in pinned SDK), When the spike report is reviewed, Then the Dev Agent Record raises a blocker (per `feedback_dreamball_ac_scope_retreat`) and proposes the documented fallback (two-call preview/commit idiom per requirements.md Assumption #9); the story does NOT silently substitute a different confirmation mechanism.
- **AC6** [grep audit — MCP tools wrap client, not store directly]: Given the generated tool spec, When `grep -E "from\\s+['\\\"]\\.\\./generated/palace-client|from\\s+['\\\"]\\.\\./store" src/lib/generated/palace-mcp-tools.ts` runs, Then matches show ONLY the client import; no direct store import (D-034 grep audit per Story 4.1 AC5 generalizes here).

## Technical Notes
- This story is BOTH the projection (AC1, AC2, AC4) AND the elicitation spike (AC3) per D-024 spike-before-promote discipline. If the spike succeeds, the projection wires elicitation natively; if it fails, the story raises a blocker for ADR amendment.
- Per requirements.md Assumption #9: if MCP elicitation is missing in the pinned SDK, the documented fallback is two-call preview/commit (preview returns a confirmation token; commit consumes it). Implementing the fallback is OUT of THIS story's scope — it's the blocker resolution path, not the default.
- The MCP server entrypoint (the `bun run mcp` runtime that hosts the generated tool spec) is Story 4.3 — this story authors the spec; Story 4.3 wires the runtime.
- Per IC2: actions invoked via MCP serialize to the existing signed-action envelope shape; no new envelope fields.
- Per D-034 / AC5: tools call the generated client (Story 4.1), not the store directly. Layering: MCP → client → store → bridge → CAS.

## Scope Boundaries
- This story DOES: ship the generated MCP tool spec; run + record the elicitation spike; route `requiresConfirmation` through elicitation OR raise a blocker per AC5.
- This story does NOT: ship the MCP server entrypoint runtime (Story 4.3); migrate any bridge sites beyond Story 4.1's; implement the fallback if elicitation is missing (that's a blocker-resolution path).
