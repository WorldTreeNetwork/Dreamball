# Story 4.1: Generate `@dreamball/palace-client` TypeScript Client + Migrate One Bridge Site

**User Story**: As an agent caller, I want a generated `@dreamball/palace-client` TypeScript module exposing each Memory Palace action as a typed function (`mint({ name, mythosTemplate }) → { palaceFp }`) that wraps the existing D-007 store wrapper, with at least one existing `src/lib/bridge/*` mutation site migrated to call the generated client and continuing to satisfy its existing Vitest coverage, so that programmatic callers no longer hand-write per-action invocation code.
**FRs**: FR8
**Decisions**: D-019 (action manifest as universal contract), D-022 (bridge pattern preserved underneath), D-034 (client wraps D-007; D-007 unchanged), D-035 (closed sets typed accordingly), IC2 (envelope shape frozen), IC6 (store API unchanged)
**Complexity**: medium
**Test Tier**: smoke

## Acceptance Criteria
- **AC1** [happy — client generated]: Given Story 3.1's authored manifest and the codegen flow from Story 1.3, When `bun run codegen` runs, Then `src/lib/generated/palace-client.ts` (or the package-aliased path agreed in Phase 3) is emitted with NFR9 provenance header, exporting one typed async function per manifest action: `mint`, `inscribe`, `addRoom`, `renameMythos`, `move`.
- **AC2** [happy — typed call site]: Given a Bun script `import { mint } from '@dreamball/palace-client'`, When `await mint({ name: 'foo', mythosTemplate: 'basic' })` is called, Then it returns a typed `{ palaceFp: string }` value; TypeScript compile-errors at any call site if input/output drifts from the manifest (verified via a `tsd`-style or `vitest --typecheck` test).
- **AC3** [happy — bridge migration site]: Given one existing `src/lib/bridge/palace-mint.ts` (or the chosen migration site), When the site is rewritten to call `import { mint } from '@dreamball/palace-client'`, Then its existing Vitest coverage (`src/lib/bridge/palace-mint.test.ts` or equivalent) continues to pass without test modifications; the underlying mutation still composes the bridge pattern (D-022) via the store wrapper (D-007).
- **AC4** [happy — D-007 audits unchanged per IC6]: Given the post-migration tree, When the existing AC7-style audit `grep -RE '__rawQuery' src/ --include='*.ts'` runs, Then the only matches are still inside `src/memory-palace/store.ts` (or the existing sanctioned site); no drift. D-007's load-bearing audit invariant is preserved (per `active-decisions.md`: "zero `__rawQuery` drift across 15 stories").
- **AC5** [grep audit per D-034 §Consequences — client never imports LadybugDB primitives]: Given the generated client, When `grep -E '@ladybugdb|kuzu' src/lib/generated/palace-client.ts` runs, Then results are zero — the client always goes through `src/memory-palace/store.ts` (per D-034 acceptance: "generated client never imports LadybugDB primitives directly").
- **AC6** [error — manifest drift compile-errors]: Given the manifest is mutated to remove `mint.inputs.properties.name`, When `bun run codegen` runs and `bun run check` runs, Then either codegen fails or the call site `mint({ name: 'foo' })` becomes a TypeScript error; drift cannot land silently.
- **AC7** [happy — full smoke + check green]: Given the migration, When `bun run check` and `bun run test:unit -- --run` run, Then both pass with no test modifications other than at the migration site (and possibly its imports).

## Technical Notes
- Per D-034: the generated client is the *external (callsite) API*; D-007 store wrapper remains the *internal (mutation primitive) API*. Two layers, both intentional, no consolidation.
- Per IC6: store API shape stays exactly as is. The generated client is a NEW caller of D-007, not a replacement.
- Choose the migration site that has the simplest existing Vitest coverage (likely `palace-mint.ts`); migrating one site proves the contract — Stories 4.2/4.3 / sprint-003 migrate the rest as opportunistic cleanup.
- The `@dreamball/palace-client` package alias vs path import is a Phase 3 decision; either works as long as it's stable. Recommend a `paths` entry in `tsconfig.json` pointing at `src/lib/generated/palace-client.ts` to avoid publishing a real npm package this sprint.
- Per D-022: the bridge pattern is composed BENEATH the client — the client calls `store.mint(...)` which calls into the existing Zig staging → Bun bridge → promote-on-success pipeline. The client adds typing + manifest-driven dispatch; it does not bypass the bridge.

## Scope Boundaries
- This story DOES: ship the generated TS client; migrate ONE bridge site (mint); verify D-007 audits + smoke + check.
- This story does NOT: migrate ALL bridge sites (sprint-003 cleanup); ship MCP projection (Story 4.2); ship MCP server entrypoint (Story 4.3); modify D-007 or its audits.
