# Story 8.1 [STRETCH]: Author `dreamball/guestbook@0.1.0` JSON Schema + Pin + Per-Archiform Codegen

**User Story**: As an archiform author, I want a tiny second archiform `dreamball/guestbook@0.1.0` authored end-to-end through the new pipeline (JSON Schema → pin → per-archiform codegen → Zig + TS + Valibot + Cypher outputs), so that the federation hypothesis ("anyone can author a new archiform") is exercised by code rather than only by infrastructure.
**FRs**: (no FRs — purely additive integration test)
**Decisions**: D-017 (3-layer model), D-018 (per-archiform JSON Schema), D-029 (pin file format), D-031 (trust model), TC3, TC8
**Complexity**: medium
**Test Tier**: thorough

## Acceptance Criteria
- **AC1** [happy — guestbook schema authored]: Given a tiny scope (e.g., one entry type with `author`, `message`, `timestamp` fields), When `schemas/guestbook-0.1.0.json` is authored, Then it validates against draft 2020-12 metaschema; the schema declares one type (e.g., `Entry`) and one action (e.g., `sign`).
- **AC2** [happy — pin recorded]: Given the schema, When `bun run schemas:pin schemas/guestbook-0.1.0.json` runs, Then `schemas/.pins/guestbook-0.1.0.fp` contains exactly the hex-encoded blake3 of the schema bytes (per D-029).
- **AC3** [happy — per-archiform codegen]: Given the pinned schema, When `bun run codegen` runs, Then per-archiform codegen emits Zig type extensions to `src/lib/generated/guestbook.types.ts` (and equivalents), Valibot validators, and Cypher DDL extensions; all outputs carry NFR9 provenance headers naming the guestbook pin as source.
- **AC4** [happy — pin verification works for second archiform]: Given the pin, When the schema is mutated by one byte and `bun run codegen` runs, Then the build fails per D-029 verification (proves pin verification generalizes beyond Memory Palace).
- **AC5** [happy — full gate set green]: Given the new archiform's outputs, When the full gate set runs (`zig build test`, `zig build smoke`, `bun run check`, `bun run test:unit -- --run`, `scripts/cli-smoke.sh`, `scripts/server-smoke.sh`, `tests/e2e-cryptography.sh`), Then all 7 gates pass — adding a new archiform must not regress existing gates.
- **AC6** [edge — D-031 lifecycle coupling acknowledged]: Given the schema declares the `sign` action with `implementation.wasm: <fp>` (Story 8.2 fills this), When the author updates the wasm in Story 8.2, Then this story's manifest entry MUST also update — and the schema reissue is documented as the natural lifecycle event per D-031 (acknowledged inline in the schema's `$comment` or in `actions/guestbook/README.md`).

## Technical Notes
- "Tiny" is the operative constraint — the second archiform is a federation PROOF, not a feature. One type, one action, no business logic beyond what the proof requires.
- Per Phase 2A `architecture-decisions.md` §"One soft constraint surfaced for Phase 3 attention": the D-031 lifecycle coupling is explicit for Cluster I — the author must understand that wasm bug fixes require schema reissue. This story acknowledges the coupling in the archiform's README.
- Place the archiform sources under `actions/guestbook/` (mirroring `actions/mint/` from Story 5.4). Add a one-paragraph `actions/guestbook/README.md` documenting the federation-proof intent + the D-031 lifecycle coupling note.
- Per `feedback_dreamball_ac_scope_retreat`: if the new archiform exposes a host-import surface gap (a primitive guestbook needs that the locked 5 don't provide), raise a blocker — do NOT silently extend `dreamball.*`.

## Scope Boundaries
- This story DOES: ship the second archiform's schema + pin + codegen output + lifecycle-coupling doc note.
- This story does NOT: author the wasm action (Story 8.2); project to CLI (Story 8.3); add aspects.sh-side publishing (out of sprint-002 scope per TC6 vendor-first).
