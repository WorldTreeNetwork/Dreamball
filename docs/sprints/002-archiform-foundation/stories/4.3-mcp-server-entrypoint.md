# Story 4.3: MCP Server Entrypoint (`bun run mcp`)

**User Story**: As a release engineer, I want a `bun run mcp` entrypoint that hosts the generated MCP tool spec and routes invocations through the generated TS client, so that a Memory Palace MCP server is invokable end-to-end and an LLM agent can drive every manifest-declared action.
**FRs**: FR9
**Decisions**: D-019, D-034 (client wraps store), TC7 (pinned MCP SDK)
**Complexity**: small
**Test Tier**: smoke

## Acceptance Criteria
- **AC1** [happy — entrypoint exists]: Given Stories 4.1 + 4.2's outputs, When `bun run mcp` is invoked, Then a Memory Palace MCP server starts on stdio (or pinned-SDK default transport), advertises the generated tool spec, and accepts tool invocations.
- **AC2** [happy — end-to-end invocation]: Given the running server + a synthetic MCP client (Vitest test under `tests/mcp/server-smoke.test.ts`), When the test invokes `palace.mint` with valid inputs, Then the response carries a typed `{ palaceFp }` shape; the underlying mutation composes the client → store → bridge → CAS pipeline.
- **AC3** [edge — confirmation surfaces via elicitation OR documented fallback]: Given the `rename-mythos` tool, When the test invokes it, Then the server EITHER surfaces an MCP elicitation step (if Story 4.2 AC3 spike passed) OR returns the documented fallback (two-call preview/commit) per Story 4.2's blocker resolution; behavior matches whichever path Story 4.2 landed.
- **AC4** [error — invalid input rejected]: Given the running server, When the test invokes `palace.mint` with invalid input `{ name: 123 }` (number, not string), Then the server returns an MCP tool-call error sourced from the shared Valibot validator; no mutation attempt occurs.
- **AC5** [happy — script wired in package.json]: Given the entrypoint, When `cat package.json | jq '.scripts.mcp'` runs, Then the script is present and points at the entrypoint (e.g., `bun src/mcp/main.ts`); CI does not run this server (it's a manual runtime), but the smoke test in AC2 covers programmatic invocation.

## Technical Notes
- Keep the entrypoint thin: import the generated tool spec, instantiate the pinned MCP SDK's server, register tools, start. The "intelligence" lives in the manifest + generated client.
- Use stdio transport by default (matches the pinned MCP SDK convention); document the runtime invocation path in Epic 7's doc refresh.
- Per D-034: tools call the client; client calls store; store uses bridge — no new mutation primitives in the MCP layer.
- Don't add a `JELLY_MCP_NO_LISTEN=1` mock-seam unless needed; the synthetic client in AC2 should drive the in-process server directly without needing a network listener.

## Scope Boundaries
- This story DOES: ship the entrypoint; verify end-to-end invocation; wire the package.json script.
- This story does NOT: change the tool spec (Story 4.2); change the client (Story 4.1); ship REST projection (Cluster L deferred); ship in-renderer projection (Cluster L deferred).
