# Story 1.1: Codegen Inversion Spike — Round-Trip Three Complex Zig Types

**User Story**: As a Dreamball maintainer, I want a spike that round-trips the three most expressively complex Zig types (envelope, sealed body, signature tier wrapper) through hand-authored JSON Schema and back to byte-identical Zig+TS+Valibot+CBOR outputs, so that Assumption #1 in `requirements.md` (JSON Schema draft 2020-12 can fully express the current Zig type system without expressivity loss) is validated before scaling to the full root.
**FRs**: FR1, FR2, FR3
**Decisions**: D-018, D-024 (spike-before-promote), D-030, D-035, NFR1
**Complexity**: large
**Test Tier**: thorough

## Acceptance Criteria
- **AC1** [happy — round-trip]: Given hand-authored JSON Schema fragments for `Envelope`, `SealedBody`, and `SignatureTierWrapper` (the three most expressively complex Zig types per Assumption #1), When the spike consumer in `tools/schema-gen/spike/main.zig` reads them and emits Zig + TS + Valibot + CBOR codecs to `tools/schema-gen/spike/out/`, Then the emitted Zig types compile and decode a sample envelope into the same in-memory representation as the legacy generator produces.
- **AC2** [byte-equivalence on the three types]: Given the spike outputs and the legacy generator outputs scoped to the same three types, When `diff -r tools/schema-gen/spike/out/ tools/schema-gen/legacy-spike-fixture/` runs, Then the diff is empty (byte-identical for the spike scope per NFR1, including provenance headers per NFR9).
- **AC3** [error — expressivity gap]: Given a Zig type construct that JSON Schema draft 2020-12 cannot natively express (e.g., a discriminated-union over CBOR tags), When the spike author encounters it, Then the spike report at `docs/decisions/2026-04-XX-codegen-spike-findings.md` records the construct, the chosen normalization (Schema dialect extension, naming convention, or `$comment` marker), and a Phase 3 follow-up note; the spike does NOT silently substitute (per `feedback_dreamball_ac_scope_retreat`).
- **AC4** [decision-promote]: Given the spike completes green, When the spike report is reviewed, Then a one-paragraph "spike outcome → architecture commitment" entry is appended to `docs/decisions/2026-04-XX-codegen-spike-findings.md` confirming D-018 + D-030 are sufficient (or proposing an amendment).

## Technical Notes
- Spike location is intentionally siloed (`tools/schema-gen/spike/`) so it does not perturb the legacy generator until Story 1.4's shadow phase wires both side-by-side.
- Use the existing `src/protocol_v2.zig` types as the legacy reference; copy the relevant struct decls into a `legacy-spike-fixture/` snapshot once at spike start so byte-equivalence diffing is reproducible.
- The spike's CBOR codec emission MUST defer to the canonical Zig CBOR encoding rules (D-018: "CBOR algorithm stays canonical in Zig"); the spike does NOT re-author CBOR encoding semantics.
- Include the `bun run codegen` runtime budget check (NFR2 ≤ 5 s) in the spike harness even at this scale — early signal on perf trajectory.

## Scope Boundaries
- This story DOES: validate Assumption #1 against the three named types; emit a spike report; commit the spike code under `tools/schema-gen/spike/` for follow-on stories to inherit.
- This story does NOT: author the full `schemas/root-2.0.0.json` (Story 1.2); build the production per-target generators outside `spike/` (Story 1.3); set up the shadow phase (Story 1.4); cut over (Story 1.5).
