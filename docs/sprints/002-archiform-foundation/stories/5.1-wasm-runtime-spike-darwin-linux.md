# Story 5.1: Wasm Runtime Spike — Choose Runtime; Minimal Host Loads `hello.wasm` on darwin + linux

**User Story**: As a Dreamball maintainer, I want a spike that selects a wasm runtime (Zig std `wasm` vs `wasmtime`/`wasmer` C ABI) and demonstrates a minimal Zig wasm host loading and instantiating a `hello.wasm` guest module under WASI on both darwin and linux without source divergence, so that Assumption #2 (WASI cross-platform parity inside `jelly` CLI) is validated and D-032's "single shared host code" commitment is grounded.
**FRs**: FR10
**Decisions**: D-020 (wasm runtime), D-024 (spike-before-promote), D-032 (single shared Zig host; CLI + browser targets), TC4 (WASI + dreamball.* only), TC7 (Zig 0.16.0 pinned)
**Complexity**: large
**Test Tier**: thorough

## Acceptance Criteria
- **AC1** [happy — runtime selected + documented]: Given the spike, When the runtime selection is made (Zig std `wasm` runtime OR linked `wasmtime`/`wasmer` C ABI), Then the choice is recorded in `docs/decisions/2026-04-XX-wasm-runtime-selection.md` with: trade-offs evaluated, build-size impact (TC5 budget consideration), cross-platform parity confirmation, and the chosen runtime's instantiation API surface.
- **AC2** [happy — minimal host loads `hello.wasm` on darwin]: Given the chosen runtime + a `hello.wasm` guest module (compiled from a small Zig source under `tests/wasm/hello/`), When the spike host at `src/wasm-host/spike/main.zig` loads + instantiates the module on darwin, Then it executes `hello.wasm`'s exported `main` function and observes the expected output.
- **AC3** [happy — same host loads `hello.wasm` on linux]: Given the same Zig host source + same `hello.wasm`, When the spike runs in CI on linux (Ubuntu in `.github/workflows/ci.yml`), Then it executes successfully with the SAME output as AC2 (no per-platform divergence in host code beyond linker/runtime configuration).
- **AC4** [edge — WASI capability brokering works]: Given a `hello.wasm` guest that calls a single WASI primitive (e.g., `fd_write` to stdout), When the host runs it, Then the host brokers the WASI call (per TC4: WASI imports are mediated by host); guest output appears on host stdout.
- **AC5** [error — non-WASI import rejected]: Given a `hello-bad.wasm` guest that imports `env.malicious_function`, When the host attempts instantiation, Then instantiation fails with a clear structured error naming the offending import (per SEC1: host-import whitelist; the spike validates the rejection mechanism even though the full `dreamball.*`-only enforcement lands in Story 5.3).
- **AC6** [perf — instantiation budget per NFR4]: Given the spike, When `hello.wasm` (sub-1 MB) is loaded + instantiated cold, Then wall-clock measured instantiation completes in ≤ 100 ms on the M-series Mac baseline (per NFR4); CI publishes the measured time.
- **AC7** [error — blocker discipline]: Given AC3 (linux parity) fails OR AC6 (perf budget) fails, When the spike report is filed, Then the Dev Agent Record raises a blocker (per `feedback_dreamball_ac_scope_retreat`) and proposes either: (i) ADR amendment to D-032 allowing per-platform host shims, or (ii) ADR amendment to NFR4 with measured baseline; story does NOT silently substitute a different runtime or relax the budget.

## Technical Notes
- Per D-024, this is THE spike for Cluster E. Architectural decisions made here flow into Stories 5.2–5.5.
- Runtime trade-off considerations: Zig std `wasm` is in-tree (no extra deps, smaller binary, may have feature gaps); `wasmtime`/`wasmer` C ABI is mature but adds a C dep + binary size. Document the chosen path's reasoning per AC1.
- The spike host code lives at `src/wasm-host/spike/main.zig` — siloed from production paths. Story 5.2 promotes the architecture into `src/wasm-host/main.zig` with the production import surface.
- Per D-032: the same Zig source must compile to both CLI (Zig+WASI) and (in sprint-003) browser (`jelly.wasm`-style). This story tests CLI-side only; the browser-side compilation is Story 5.5's concern (or a sprint-003 follow-on).
- Cross-platform parity test (AC3) MUST run in CI's linux job (already exists in `.github/workflows/ci.yml`); add a `wasm-spike` test target.
- Per `feedback_dreamball_ac_scope_retreat`: if the spike hits a hard runtime blocker, raise it. Do NOT silently substitute a JS-side fallback or a polyfilled WASI shim.

## Scope Boundaries
- This story DOES: select runtime; ship minimal CLI host loading `hello.wasm` on darwin + linux; record runtime decision ADR; validate Assumption #2.
- This story does NOT: implement the 5 `dreamball.*` imports (Story 5.2); ship verify-before-instantiate / import-violation / memory-limit failure paths (Story 5.3); ship sample `mint.wasm` end-to-end (Story 5.4); author `docs/dreamball-imports.md` (Story 5.5); ship browser-side compilation (sprint-003).

### Completion Notes per AC

- **AC1 — runtime selected + documented**: `docs/decisions/2026-04-28-wasm-runtime-selection.md` records trade-offs across (A) in-tree Zig interpreter, (B) wasmtime C ABI, (C) wasmer C ABI. Choice = **Option A** because it is the only option compatible with D-032's "single shared host code" commitment (wasmtime/wasmer are not available in the browser). The ADR documents the instantiation API surface, build-size impact (no new deps; a few KB of Zig vs. multiple MB for wasmtime), cross-platform parity (one Zig source compiles for darwin + linux + wasm32-freestanding), and growth path through Stories 5.2/5.3.
- **AC2 — host loads hello.wasm on darwin**: `zig build wasm-spike-host` on darwin/M-series prints `HELLO_FROM_DREAMBALL_SPIKE` followed by `spike: hello.wasm wrote: HELLO_FROM_DREAMBALL_SPIKE`. Spike host: `src/wasm-host/spike/main.zig`, runtime: `src/wasm-host/spike/runtime.zig`, hand-authored guest bytes: `src/wasm-host/spike/build_hello.zig`.
- **AC3 — same host loads hello.wasm on linux**: CI step added in `.github/workflows/ci.yml` (Zig job) named `wasm-spike (Story 5.1 — AC3 linux parity, AC6 perf publish)`. The step runs the *identical* `zig build wasm-spike-host` invocation as darwin and greps for the AC2/AC4/AC5/AC6 success markers. Same Zig source — no per-platform divergence beyond the platform-default `target` zig auto-selects. **Note**: this single-machine restart cannot itself observe the linux run; the CI gate is the verification surface. Per `feedback_dreamball_ac_scope_retreat`, if the CI gate fails on linux, the resolution is a blocker (raise an ADR amendment to D-032), not a silent shim.
- **AC4 — WASI capability brokering**: `wasiFdWrite` in the spike host translates the guest's `(fd, iovs_ptr, iovs_len, nwritten_ptr)` arguments through guest linear memory, writes the bytes to host stdout via `std.Io.File.stdout()`, and writes the success errno + nwritten count back into guest memory. Output appears on host stdout; guest sees errno=0.
- **AC5 — non-WASI import rejected**: `hello-bad.wasm` (built by `build_hello.buildHelloBad`) imports `env.malicious_function`. `runtime.Instance.init` walks the module's import table and matches each entry against the host-supplied whitelist (only `wasi_snapshot_preview1.fd_write` for the spike). The unmatched import causes `Error.UnknownImport`; the spike host then prints `spike: hello-bad.wasm rejected import env.malicious_function`. Story 5.3 will harden this path with structured error codes, full `dreamball.*`-only enforcement, and a dedicated negative-test suite.
- **AC6 — instantiation budget**: cold parse + instantiate measured at **~1.2 ms** on M3 Max (`spike: cold instantiation = 1220 us (budget 100000 us)`), comfortably under NFR4's 100 ms budget. The spike host exits non-zero if the budget is exceeded — no silent budget relaxation. CI publishes the measured time on linux as well.
- **AC7 — blocker discipline**: the spike host uses non-zero exit codes (`2` for budget overrun, `3` for missed import rejection) rather than silently substituting. AC3/AC6 failure modes are explicitly documented in the runtime-selection ADR's "Open questions deferred" + "Consequences" sections.

### Problems encountered

- The previous executor was interrupted with only an empty `tests/wasm/hello/main.zig` placeholder. Replaced with a documenting source file describing the equivalent guest program; the actual canonical bytes are hand-authored in `src/wasm-host/spike/build_hello.zig` so the spike's interpreter scope stays auditable (every opcode in the guest is one the interpreter knows). Story 5.2 grows opcode coverage to handle Zig→wasm-compiled guests directly.
- Zig 0.16.0 surface differences: `std.heap.GeneralPurposeAllocator` is gone (use `std.heap.DebugAllocator` or `init.gpa` from `std.process.Init`); `std.time.Timer` is gone (use `std.Io.Clock.awake.now(io)` and `Timestamp.durationTo`); `std.mem.trimRight` renamed to `trimEnd`; unmanaged `ArrayList` requires `: T = .empty` initializer rather than `T{}`. All adapted in this story's code.
- First run of the spike crashed with `OutOfBounds` because the ciovec struct was placed at offset 27 (immediately after the marker) but the guest pushed `i32.const 28` for `iovs_ptr`. Added one byte of alignment padding to `build_hello.buildHello` to make ciovec sit at the 4-byte-aligned offset 28.
