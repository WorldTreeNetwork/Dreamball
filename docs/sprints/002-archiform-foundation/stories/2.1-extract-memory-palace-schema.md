# Story 2.1: Extract Memory Palace Types into `schemas/memory-palace-0.1.0.json` + Pin

**User Story**: As an archiform author, I want Memory Palace types (`Inscription`, `Room`, `Aqueduct`, traversal state, decay parameters, `Triple`, `Mythos`, `Agent` extensions) extracted from `src/protocol_v2.zig` and `src/memory-palace/schema.cypher` into a single vendored `schemas/memory-palace-0.1.0.json` with a pinned blake3 fp, so that Memory Palace becomes one archiform among many — declared in JSON Schema, fp-pinned, and ready for per-archiform codegen.
**FRs**: FR4
**Decisions**: D-017 (3-layer model; schema-layer archiform), D-018 (per-archiform JSON Schema), D-028 (Triple-native KG schema citizens), D-029 (pin file format), TC3, TC8, IC1
**Complexity**: medium
**Test Tier**: smoke

## Acceptance Criteria
- **AC1** [happy — schema authored]: Given `src/protocol_v2.zig` Memory Palace types and `src/memory-palace/schema.cypher`, When `schemas/memory-palace-0.1.0.json` is authored, Then the schema declares (at minimum): `Inscription`, `Mythos`, `Triple` (per D-028), `MemoryNode`, `MemoryConnection`, `Memory`, `KnowledgeGraph`, `Room`, `Aqueduct` (with all 6 properties: `resistance`, `capacitance`, `strength`, `conductance`, `phase`, `last_traversal_ts`), `Palace`, and `Agent` extensions (`personality_master_prompt`, `memory`, `emotional_register`, `interaction_set`); validates against draft 2020-12 metaschema.
- **AC2** [happy — pin recorded per D-029]: Given the authored schema, When `bun run schemas:pin schemas/memory-palace-0.1.0.json` runs, Then `schemas/.pins/memory-palace-0.1.0.fp` contains exactly the hex-encoded blake3 of the canonical schema bytes (one line, no trailing newline normalization, per D-029 Option A).
- **AC3** [happy — coverage assertion]: Given the schema, When `tests/codegen/memory-palace-schema-coverage.test.ts` runs, Then every Memory Palace type currently in `src/protocol_v2.zig` and every node/edge table in `src/memory-palace/schema.cypher` has a corresponding entry in the schema; missing types fail the test naming the gap.
- **AC4** [edge — Triple as schema citizen per D-028]: Given the authored schema, When `Triple` is inspected, Then it declares the `fp` MERGE key with derivation note `blake3(agent_fp || \\0 || subject || \\0 || predicate || \\0 || object)` (per D-028) AND the `HAS_KNOWLEDGE` rel from `Agent` to `Triple` is declared; the legacy `Agent.knowledge_graph STRING` field is NOT in the schema (removed per D-028).
- **AC5** [error — pin mismatch fails build]: Given the pin file, When the schema is mutated by one byte and `bun run codegen` runs, Then the build fails per D-029 (same mechanic as Story 1.2 AC4) — verifies pin verification works for per-archiform schemas.

## Technical Notes
- This is a translation exercise — no semantic change. The schema MUST be a faithful representation of what the existing code already does; semantic deltas are out of scope.
- Recrypt naming inheritance (TC9): every type/field name MUST match its recrypt-aligned name verbatim where overlap exists.
- Per IC1: `archiform_fp` extension to genesis envelope is additive back-compat; this story does NOT add the field (Story 2.3 does), but the schema MAY declare the optional field surface so the codegen flow is ready.
- Per D-021/D-022: Memory Palace mutation paths inherit logical commit-ordering + bridge pattern; the schema does not encode transactional semantics — those live in code/CLI/wasm host.
- Action-manifest entries are added to the schema in Epic 3 (Story 3.1); this story authors the type-shape portion only.

## Scope Boundaries
- This story DOES: ship `schemas/memory-palace-0.1.0.json` + `schemas/.pins/memory-palace-0.1.0.fp` + the coverage test.
- This story does NOT: run per-archiform codegen producing Cypher/TS/Zig outputs (Story 2.2); add `archiform_fp` to genesis envelope (Story 2.3); add action manifest entries (Story 3.1); change any wire-format bytes.
